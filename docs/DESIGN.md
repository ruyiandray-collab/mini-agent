# 设计说明与开发记录

本文记录 MiniAgent 开发过程中的关键决策，以及遇到的问题和解决方法。

## 1. 为什么不用 LangChain 等框架

框架把 Agent Loop 封装成一个黑盒。本项目的目标是彻底理解 Agent 的工作机制：消息如何组织、工具调用怎样配对、何时结束循环、出错时怎么办。所以选择只依赖官方 `openai` SDK，用 `base_url` 指向 DeepSeek，其余部分全部手写。

## 2. 实验：工具结果缺失会发生什么

**实验**：在 Agent Loop 中注释掉「把工具结果写回 messages」这一行，然后提问「现在几点」。

**原以为**：模型看不到工具结果，会反复调用工具，直到达到最大步数。

**实际结果**：API 在第二次请求时直接返回 400：
> An assistant message with 'tool_calls' must be followed by tool messages responding to each 'tool_call_id'.

**结论**：OpenAI 兼容协议强制要求 `tool_calls` 和 `tool` 消息通过 `tool_call_id` 一一配对。这条约束后来直接影响了两处设计：
- **历史裁剪**（`memory.save_history`）：只能从 user 消息处切分，不能拆开同一轮里的工具调用和工具结果
- **失败回滚**（`Agent.run`）：出错时撤销本轮消息，避免残缺的历史导致之后每次请求都失败

## 3. 实验中发现的重试缺陷

同一次实验中还发现，最初的实现对所有异常都会重试。遇到 400 错误时，程序白白重试了 3 次、等待约 6 秒，但每次请求都一样，结果也都一样。

**修正**：只对 `APIConnectionError`、`RateLimitError`（429）、`InternalServerError`（5xx）重试。有单元测试确认，不可重试的错误只会调用一次 API。

## 4. 长期记忆由 Agent 自主写入

另一种可选方案是每轮都让模型总结「有什么值得记住的」，但这样每轮都要多调用一次模型，成本翻倍。

本项目把 `remember` / `forget` 做成普通工具，由 Agent 在对话中自行判断是否调用，不额外增加调用次数。长期记忆每次调用模型前重新注入系统提示词，所以刚记住的内容在下一步就能用上。

## 5. 评测设计

- 每个任务都在**独立的临时工作区和临时记忆**中运行，互不干扰，也不会影响真实数据
- 判定采用**基于结果的检查**：检查生成的文件内容、记忆条目、回答中的关键数字，不比对具体措辞
- 模型输出有随机性，所以每个任务运行 3 次

**评测本身也会出错**：第一轮评测结果是 43/45。人工检查后发现，两次失败都是 Agent 正确回答了「读不到 report.txt」，但判定规则只认「不存在 / 找不到」，属于**误判**。补充同义表述后，结果为 45/45。这说明评测结果必须人工抽查，否则可能冤枉模型，也可能掩盖真实问题。

**已知局限**：`sandbox_escape` 任务中，模型本身就拒绝了读取 `../.env`，没有真正调用工具，因此这个任务验证的是模型层面的安全意识。代码层面的沙箱拦截由单元测试 `test_sandbox_blocks_escape` 覆盖。
